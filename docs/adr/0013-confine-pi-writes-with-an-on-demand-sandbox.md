# 0013. Confine pi's writes with a sandbox turned on when wanted

- Date: 2026-10-12
- Status: Accepted

## Context

pi runs every tool with the operating-system permissions of the user who
started it. pi-automode decides whether a tool call may run, but once a call is
allowed nothing limits what it touches: a build script, a test, or a binary the
agent just downloaded can write anywhere under `$HOME` and beyond. What is
wanted is a switch that, when on, lets pi write only under the directory it was
started in and under directories named in a settings file, and that can be
turned off again in the same session. Network access stays unrestricted for
now.

The constraints:

- **pi runs on the devbox (Linux, inside Docker) and on a Mac.**
- **The devbox cannot create unprivileged user namespaces.** Its hosts run
  Ubuntu 24.04 with `kernel.apparmor_restrict_unprivileged_userns=1`, so
  `unshare -U` fails in the container. `bwrap` in the devbox image is setuid
  root and works regardless.
- **Only part of what writes runs in a separate process.** `bash` and `bg_run`
  (`pi/extensions/background-bash.ts`) spawn processes that an OS sandbox can
  enclose. `write` and `edit` run inside the pi process, which no OS sandbox
  around a child can reach.
- **Unix sockets lead out of any sandbox.** The herdr server runs commands in
  panes on request; the devbox user is in the `docker` group and
  `/var/run/docker.sock` is present; tmux and ssh-agent sockets are there too.
  A sandboxed process that can connect to one of them can have anything done
  unconfined. herdr is still expected to work by default.
- **herdr-tasks workers run in git worktrees.** A worktree's `.git` is a file
  pointing into the main repository's `.git`, outside the worktree, so a commit
  writes outside the directory pi was started in.
- **Builds write caches under `$HOME`** (`~/.cache`, `~/.npm`, Go's module
  cache, `~/.cargo`). Without them most builds fail.
- **Some files in a working tree are run later, outside any sandbox:** git
  hooks and `core.*` settings in `.git/config`, pi's own `.pi/extensions`,
  Claude Code's `.claude/settings.json`, `.envrc`, editor task files.
- **pi gates project configuration in `.pi/` behind project trust**
  (`~/.pi/agent/trust.json`), but only for the resources it knows. A `.pi`
  holding nothing else is not trust-gated, and `ctx.isProjectTrusted()`
  returns true there without anyone having been asked.

## Decision

**A pi extension, `pi/extensions/sandbox/`, runs `bash` and `bg_run` commands
in an OS sandbox and checks `write` and `edit` paths in a `tool_call` handler,
both against the same write allowlist. Only the user turns it on or off.**

- **Enforcement on Linux: bubblewrap, called directly.** The root filesystem
  is bound read-only, the allowlist is bound writable on top, and denied paths
  are bound read-only on top of that. The command gets a fresh `/dev`, its own
  PID namespace and `/proc`, and a new session. The network namespace is
  shared, so the network is untouched. A seccomp filter generated by the
  extension (x86-64 and arm64) makes `socket(AF_UNIX, …)` and `io_uring_*`
  fail with `EPERM`; it is handed to bwrap through a pipe, never a file the
  sandbox could replace.
- **Enforcement on macOS: `@anthropic-ai/sandbox-runtime`**, with the same
  write allowlist, no network restriction (no `allowedDomains`, so no proxies)
  and Unix sockets blocked unless allowed.
- **`write` and `edit`** resolve their target with `realpath` (for a new file,
  the realpath of the nearest existing parent) and are blocked outside the
  allowlist or inside a denied path.
- **Opening the way out.** `excludedCommands` lists executables whose calls run
  outside the sandbox; the default is `herdr` and the herdr-tasks helpers
  (`~/bin/herdr-task-worktree`, `prompt-agent.sh`, `write-task-agents.sh`). A
  call is excluded only when it is a single simple command: plain words and
  quoted strings, with no `$`, backticks, operators, redirections or
  assignments. Its executable, resolved through `PATH` and `realpath` outside
  the sandbox, must be the same file an entry resolves to, and must not lie
  under a writable path (otherwise the sandbox could replace it first).
  Excluded calls still go through pi-automode. `allowAllUnixSockets: true`
  drops the seccomp filter and keeps everything else. `/sandbox off` removes
  the sandbox altogether.
- **Configuration.** Global settings are `~/.pi/agent/extensions/sandbox.json`,
  copied from `pi/config/sandbox.json` by `bin/setup-pi.sh` (never linked to
  the checkout, like pi-automode's). Project settings are
  `<cwd>/.pi/sandbox.json`, read only when `trust.json` holds a saved "trust"
  decision for the project, or pi asked and was told yes. Otherwise they are
  ignored and the user is told so. Lists (`allowWrite`, `denyWrite`,
  `denyRead`, `excludedCommands`) are the union of both files; booleans in the
  project file win.
- **Switching.** `/sandbox on`, `/sandbox off`, and `/sandbox` to show the
  state and the effective paths. `enabled` in either settings file turns it on
  at startup, and `--sandbox` / `--no-sandbox` override that for one process.
  No tool lets the model change the state. The footer shows when it is on.
- **Write allowlist.** Built in: the launch directory, `/tmp` and `$TMPDIR`.
  The shared global settings add the language tools' caches.
- **Always denied.** In the launch directory and each configured writable
  path: `.git/hooks`, `.git/config`, `.git/config.worktree`, `.pi`, `.claude`,
  `.vscode`, `.idea`, `.envrc`, `.mcp.json`, `.gitmodules`, `.gitconfig`,
  `.ripgreprc` and the shell rc files. Also the global settings file.
- **git worktrees.** When the launch directory is a worktree, the main
  repository's `.git` (`git rev-parse --git-common-dir`) is writable, except
  its `hooks`, `config` and `config.worktree`.
- **Checked afterwards.** bwrap can only bind paths that exist, and a writable
  parent lets a denied directory be renamed away and recreated. So before each
  sandboxed command the extension records the identity (device and inode, or
  absence) of every denied path, compares it when the command ends, and
  appends a warning to the result and notifies the user when one changed.
- **Reads and network are not restricted.** `denyRead` can be set but is empty
  by default.
- **Running `bg_run` jobs keep the state they started with.** Switching does
  not stop them; turning the sandbox on lists the jobs still running
  unconfined. `background-bash.ts` asks the sandbox extension to wrap each
  command over pi's shared event bus.
- **The model is told.** On a switch, a message states the state, the
  writable paths and the excluded commands. A blocked `write`/`edit` returns a
  reason, and a `bash` result that reports a read-only file system or a
  refused socket gets a note. Both say the denial came from the sandbox and
  must be reported to the user, not worked around.
- **Tests.** Settings, trust, path resolution, simple-command matching, the
  denied paths and the bwrap arguments live in modules that do not import pi
  and are unit-tested with `node --test`, run from bats. A bats integration
  test runs real bubblewrap and checks that writes outside the allowlist, to
  `.git/hooks`, and creating a Unix socket all fail; it is skipped where
  bubblewrap cannot run.

## Alternatives considered

**Sandbox `bash` only, as pi's example extension does.** `edit` and `write`
would still write anywhere, which defeats the purpose.

**`@anthropic-ai/sandbox-runtime` on Linux too.** On the devbox it fails twice:
with defaults bwrap cannot mount `/proc`, and with `enableWeakerNestedSandbox`
its `apply-seccomp` helper cannot create the nested user namespace it needs.
It runs only with `allowAllUnixSockets: true`, which leaves herdr and
`docker.sock` reachable. Turning off `apparmor_restrict_unprivileged_userns` on
the hosts would fix that by weakening every host for one tool.

**Hide known sockets instead of blocking socket creation.** Binding over
`docker.sock`, herdr's session directory and the like is a denylist: any socket
not listed stays open.

**Allow a worktree's whole main `.git` including `hooks` and `config`.** A hook
or `core.fsmonitor` written there runs unconfined the next time git is used
outside the sandbox.

**Read project settings when `ctx.isProjectTrusted()` is true.** A cloned
repository with nothing but `.pi/sandbox.json` passes that check, and could
exclude `bash` or allow writing to `/`.

**Allow only the launch directory and `/tmp`.** Nearly every build fails on its
cache. **Allow all of `$HOME` except sensitive paths.** That is a denylist, and
anything not listed is writable.

**Stop `bg_run` jobs on a switch.** herdr-tasks coordinators wait on workers
with long-running `herdr agent wait` jobs, which write nothing; stopping them
loses the wait.

## Consequences

- Within a session the boundary is the allowlist plus whatever an excluded
  command can do. A worker started through herdr runs unconfined unless it
  turns on a sandbox of its own.
- Compound commands that involve herdr (`herdr … | jq`, `cd x && herdr …`) run
  inside the sandbox and fail to connect. This matches the existing rule that
  herdr is called as a single command.
- When the launch directory contains an excluded helper (pi started in the
  dotfiles checkout, or in herdr-tasks), the helper is not excluded there.
- A herdr-tasks coordinator writes task notes under
  `~/.local/state/herdr-tasks`, which is not in the default allowlist; a
  coordinator session runs without the sandbox or adds it.
- Starting pi in `$HOME` makes nearly all of it writable; the extension warns
  when the launch directory is `$HOME` or above it.
- Other extensions' and MCP tools run in the pi process and are not confined.
  Only `write` and `edit` are path-checked. `!` commands typed by the user are
  not sandboxed.
- With reads and network open, the sandbox does not prevent secrets from being
  read and sent elsewhere. Restricting reads belongs with restricting the
  network.
- Denied paths are protected only directly under each writable root. Nested
  repositories or nested `.pi` directories are not, beyond what the check
  afterwards reports.
- On Linux nothing records which write was refused. The model sees the
  command's own error and the note added to it.
- The macOS path is built on sandbox-runtime and is not exercised by the
  devbox's tests. The extension's `package.json` pulls it in, so
  `bin/setup-pi.sh` runs `npm ci` in the extension's directory and Renovate
  tracks the version.
